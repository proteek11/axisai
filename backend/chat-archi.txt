Chat Feature — Full Architecture Design

Your Question #1 — Who Controls "No Answer" Messages?
Python side controls the classification. Moodle side controls the display copy. Here's the clean split:
Python returns a structured response_type enum with every response:
ANSWER           → AI found good context, confident answer
LOW_CONFIDENCE   → Answer exists but chunks scored below threshold  
NO_CONTEXT       → No relevant vectors found in this course's content
OUT_OF_SCOPE     → Question detected as irrelevant to the course topic
AMBIGUOUS        → Question needs clarification before answering
ERROR            → Something failed internally
Python also returns a default_message string for each non-ANSWER type — so if Moodle doesn't override anything, it still shows something sensible. But Moodle's PHP plugin can map each response_type to its own language string (get_string() from Moodle's lang system). This is important because:

Moodle already handles i18n properly through its lang files
Different tenants may want different tones (formal university vs casual corporate)
Python doesn't need to know about Moodle's branding

Enrollment/access errors never reach Python. Moodle validates and blocks before the API call. Python only receives requests from enrolled, authorized users — it should never need to say "you're not enrolled."

Your Question #2 — Multi-Turn Conversations
This is the most complex part. The design needs three things working together:
A. Intent Detection
Every incoming message gets classified before RAG runs:
GENERAL_QUESTION   → standard RAG answer
EXPLAIN_MORE       → user wants deeper explanation of last topic
GIVE_EXAMPLES      → user wants concrete examples
QUIZ_ME            → user wants to be tested
SHOW_VISUAL        → user wants graphical/diagram representation
SUMMARIZE          → user wants a summary of a topic
COMPARE            → user wants two things compared
FOLLOW_UP          → a continuation of the prior assistant turn
Intent detection is a fast LLM call (can use a cheaper/faster model like Haiku or GPT-4o-mini) that runs first, then the right handler kicks in. This is what enables "explain → then give me 2 questions → then show me a graph" — each message goes through intent detection and routes to the correct generator.
B. Conversation History Management
You can't send 100 messages of history to the LLM forever. Strategy:

Window: always include the last 8–10 messages as literal history
Session summary: after 15+ messages, use a background job to summarize the older portion into a "session context summary" stored on the ChatSession row. This summary is injected at the top of the prompt instead of the old messages.
Topic continuity: the session stores current_topic_tags (JSONB) — these are used to bias the RAG retrieval even when the user asks a short follow-up like "explain that more" without specifying what "that" is

C. Context-Aware RAG
When the user says "show me a graphical representation" — the RAG search needs to know they're still talking about the same topic as 3 messages ago. The system:

Looks at the last assistant message's retrieved_chunks from the DB
Re-uses those same content_item_ids as a filter for the next RAG search
Combines with fresh semantic search on the current message

This is why retrieved_chunks is stored on every ChatMessage — it's not just for citations, it's for context threading.

Your Question #3 — Suggestions
Every AI response returns a suggestions array. These are structured objects, not just strings:
json"suggestions": [
  {
    "id": "sug_1",
    "type": "follow_up_question",
    "label": "Can you give me a real-world example?",
    "action": "ask",
    "payload": "Can you give me a real-world example of this concept?"
  },
  {
    "id": "sug_2", 
    "type": "action",
    "label": "Quiz me on this",
    "action": "quiz_me",
    "payload": null
  },
  {
    "id": "sug_3",
    "type": "action", 
    "label": "Show me visually",
    "action": "visualize",
    "payload": null
  },
  {
    "id": "sug_4",
    "type": "related_topic",
    "label": "Explore: TCP/IP Model",
    "action": "ask",
    "payload": "Tell me about the TCP/IP model"
  }
]
Types of suggestions:

follow_up_question — AI-generated natural continuation (2–3 of these, contextual)
action — fixed action buttons (quiz_me, visualize, explain_more, summarize)
related_topic — semantically related topics found in the same course content (from Qdrant)

In Moodle, the action type buttons and follow_up_question chips render as clickable elements. When clicked, they send the payload as the next user message — or trigger a special action for quiz_me / visualize. The id is tracked in the next message's payload so you know which suggestion the user clicked (this feeds into the personalization data in Phase 4).
Suggestions are generated by the LLM as part of the main response — not a separate API call. The prompt instructs the model to output structured JSON at the end of its response, which the Python service parses out before returning. This keeps it one round-trip.

Full API Response Structure
json{
  "session_id": "uuid",
  "message_id": "uuid",
  "response_type": "ANSWER",
  "intent_detected": "EXPLAIN_MORE",
  "answer": "The OSI model has 7 layers because...",
  "render_hint": "markdown",
  "visual_data": null,
  "sources": [
    {
      "content_item_id": "uuid",
      "title": "Week 3 - Network Fundamentals",
      "chunk_text": "The physical layer is responsible for...",
      "relevance_score": 0.91
    }
  ],
  "confidence": 0.89,
  "suggestions": [ ... ],
  "default_message": null,
  "meta": {
    "tokens_prompt": 1840,
    "tokens_completion": 312,
    "model": "gpt-4o-mini",
    "latency_ms": 1240,
    "rag_chunks_retrieved": 4,
    "rag_chunks_used": 3
  }
}
```

When `render_hint` is `"visual"`, `visual_data` contains a chart spec (Chart.js compatible JSON) that Moodle renders directly — no image generation needed, just a JS chart from structured data. For more complex diagrams, it can return a Mermaid diagram string that Moodle renders.

### Database Changes Needed

The existing `ChatMessage` model needs these additions (new migration):
```
intent              String(30)    — detected intent for this message
response_type       String(20)    — ANSWER/NO_CONTEXT/etc.
confidence_score    Float         — 0.0–1.0
render_hint         String(20)    — text/markdown/visual/mermaid
visual_data         JSONB         — chart/diagram data if render_hint=visual
suggestions         JSONB         — the suggestions array returned
latency_ms          Integer       — end-to-end response time
suggestion_clicked  String(10)    — which suggestion_id led to this message (nullable)
```

The existing `ChatSession` needs:
```
session_summary     Text          — rolling LLM-generated summary of older messages
current_topic_tags  JSONB         — e.g. ["OSI model", "network layers"]
total_cost_usd      Numeric       — running cost total (display convenience)
```

New table for Phase 4 foundation (create now, populate from day one):
```
user_learning_events
  - id, tenant_id, moodle_user_id, moodle_course_id
  - event_type: ASKED / ASKED_EXPLAIN / ASKED_VISUAL / QUIZ_TAKEN / SUGGESTION_CLICKED
  - topic_tags: JSONB        — ["OSI model", "network layers"]
  - content_item_ids: JSONB  — which course materials were involved
  - chat_session_id, chat_message_id
  - confidence_score         — proxy for "how well covered is this topic"
  - created_at
This table is the raw material for Phase 4. Every chat interaction writes a row here automatically. By the time you build the personalization engine, you'll have real historical data to work from.

Phase 4 Personalization — What You're Building Towards
Since you wanted clarity on the bigger picture: by capturing user_learning_events from day one, Phase 4 can analyze patterns like:

Topics the user asked to explain multiple times → weak areas
Topics the user skipped over quickly → either confident or not engaging
Whether the user prefers visual responses (clicked visualize frequently)
Whether they prefer quizzing themselves vs reading
Which course materials generated the most questions (gaps in the content itself)
Session time-of-day, session length, dropout points

This feeds a user_learning_profiles table (Phase 4) that generates a personalized study plan and can surface "you asked about X 3 times but your quiz scores on it are low — here's a focused review."
