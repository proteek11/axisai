axis-ai — Technical Architecture
==================================
Last updated: April 2026


TECHNOLOGY STACK
----------------
Language        Python 3.11
Framework       FastAPI (async, ASGI via Uvicorn)
ORM             SQLAlchemy 2.0 (fully async, asyncpg driver)
Migrations      Alembic (versioned, applied on container startup)
Database        PostgreSQL 15
Vector DB       Qdrant (self-hosted or Qdrant Cloud)
Cache / RL      Redis 7
Task Queue      Celery (Redis broker) — all heavy processing is async
AI Gateway      LiteLLM (unified interface over OpenAI-compatible APIs)
Embeddings      OpenAI text-embedding-3-small (1536 dims)
LLM (fast)      gpt-4o-mini  (intent classify, cheap tasks)
LLM (main)      gpt-4o       (answer generation, content outputs)
HTTP Client     httpx (async, used by URL-fetch fallback in MoodlePageExtractor)
HTML Parsing    beautifulsoup4 (page content extraction + iframe detection)
PDF Parsing     pdfplumber
Video Captions  yt-dlp (YouTube), Vimeo API, PeerTube API
Logging         structlog (JSON, request_id on every line)
Containerised   Docker + Docker Compose (local dev)

VECTOR DATABASE (Qdrant)
--------------------------
Two collections:

axis_content_chunks  — course content
  Point: {id: UUID, vector: float[1536]}
  Payload: {tenant_id, content_item_id, moodle_course_id, moodle_cmid,
            chunk_index, title, text_preview}
  Filter: always tenant_id + moodle_course_id; optionally moodle_cmid

axis_kb_chunks  — support knowledge base
  Point: {id: UUID, vector: float[1536]}
  Payload: {tenant_id, kb_item_id, doc_type, title, language,
            chunk_index, chunk_hash, content_hash, text, is_active}
  Filter: always tenant_id
  Retrieval filter: must_not is_active=False
    (includes chunks where is_active=True OR field is absent — backward
     compatible with items ingested before is_active was added to the upsert)
  Deactivation filter: is_active=False explicitly set via set_payload()

Similarity: Cosine distance
Min score threshold: 0.35 (configurable via CHAT_RAG_MIN_SCORE env var)


CONTENT TYPE ROUTING
---------------------
Moodle sends content_type string → ingest.py validates against ContentType enum
→ pipeline.py EXTRACTOR_REGISTRY maps to extractor class:

  "pdf"       → PDFExtractor
  "youtube"   → YouTubeExtractor
  "vimeo"     → VimeoExtractor
  "peertube"  → PeerTubeExtractor
  "html_page" → MoodlePageExtractor  (Mode A: html_content metadata;
                                       Mode B: httpx URL fetch fallback)
  "scorm"     → StructuredIngestRequest path (no extractor needed)
  "h5p"       → StructuredIngestRequest path (no extractor needed)

NOTE: The old key "page" was renamed to "html_page" to match the ContentType
enum value (HTML_PAGE = "html_page"). The two systems use "html_page" end-to-end.
Do NOT re-introduce "page" as a content_type value anywhere.


PIPELINE FLOW (Celery task: run_pipeline)
------------------------------------------
  1.  Load ProcessingJob + ContentItem from DB
  2.  Mark job PROCESSING, content_item PROCESSING
  3.  Run extractor (by content_type from EXTRACTOR_REGISTRY)
  4.  Resolve source language (extractor detection > Moodle hint > "en")
  5.  Save ExtractedContent to DB
  6.  Save Transcript records (video types, all language tracks)
  7.  Chunk raw_text (strategy from job_config.options)
  8.  Embed chunks in batches (Redis-cached embeddings)
  9.  Update content_hash + chunk_count on ContentItem
  10. Upsert chunk vectors to Qdrant
  11. For each requested task (in job_config.tasks):
       a. Map task name → OutputType → generator class
       b. Generate payload (with output_language, count options)
       c. Supersede old ACTIVE outputs for that type + language
       d. Save new AIOutput record
       e. For pool types (quiz/flashcards/glossary): save to pool table
  12. Mark ContentItem READY, job COMPLETED (100%)
  On any error: mark job FAILED with traceback, content_item remains at
  last known status (does not reset to PENDING)


KB PIPELINE FLOW (Celery task: run_kb_pipeline)
-------------------------------------------------
  1.  Load ProcessingJob + KBItem from DB
  2.  Mark job PROCESSING, kb_item status=processing
  3.  Get text source:
       a. If job_config.inline_text is set → use that directly (text/file ingest
          or reindex with new content)
       b. Otherwise → fetch + scrape source_url (URL ingest)
  4.  Chunk text
  5.  Embed chunks (same batch embedder, Redis-cached)
  6.  Delete existing Qdrant vectors for this kb_item_id (always — ensures
      clean reindex on both first ingest and subsequent reindex calls)
  7.  Upsert new chunk vectors with full payload:
       {tenant_id, kb_item_id, doc_type, title, language,
        chunk_index, chunk_hash, content_hash, text, is_active=True}
  8.  Mark kb_item status=ready, is_active=True, job COMPLETED
  On error: mark job FAILED, kb_item status=failed


AUTHENTICATION FLOW
--------------------
1. Moodle plugin stores API key (issued by POST /api/v1/admin/tenants/{id}/keys)
2. Every request: Authorization: Bearer axai_<raw_key>
3. axis-ai: SHA-256 hash of raw key → lookup in api_keys table
4. If found + active + tenant active → inject tenant_id into all queries
5. Raw key never stored or logged anywhere

Multi-tenancy: tenant_id is a mandatory filter on every table query and every
Qdrant search. Cross-tenant data access is architecturally impossible via the API.


RATE LIMITING (4 layers, Redis Lua — atomic)
---------------------------------------------
Layer 1  Cooldown        chat:cd:{tenant}:{user}               TTL=2s
         (per message, set BEFORE processing — prevents race condition)

Layer 2  Session max      chat_sessions.message_count           100 msgs (default)
         (DB-side check — no Redis involved)

Layer 3  User daily msgs  chat:rl:user:day:msgs:{t}:{u}:{date}  200/day (default)
         (Redis INCR + EXPIRE, Lua for atomicity)

Layer 4  Tenant monthly   chat:rl:tenant:month:tokens:{t}:{ym}  10M tokens (default)
         (incremented post-call, best-effort — never blocks on Redis failure)

Limits configurable via:
  - tenant.settings JSONB (per-tenant defaults)
  - user_token_overrides table (per-user overrides, set via Moodle admin)
  - rate_limit_rules table (global/scope rules)

Rate limiter FAILS OPEN on Redis errors — Redis outage ≠ student lockout.


PROMPT ARCHITECTURE
--------------------
All prompts are YAML files in app/services/ai/prompts/.
Loaded at startup by prompts/loader.py with version tracking.

Each YAML defines: model, temperature, max_tokens, system prompt, user template.

intent_detect       temp=0.0  max=300    (deterministic classification)
chat_answer         temp=0.4  max=2000   (main answer generation — see below)
summary             temp=0.3  max=1000
glossary            temp=0.2  max=1500
flashcards          temp=0.3  max=2000
quiz                temp=0.2  max=3000
faq                 temp=0.3  max=1500
infographic         temp=0.2  max=2000
chapters            temp=0.2  max=1500   (video chapter markers)
mindmap             temp=0.3  max=1000
objectives          temp=0.2  max=800
blooms              temp=0.1  max=600

All prompts instruct the LLM to return valid JSON only.
parser.py strips markdown code fences before JSON parsing.
Structured output is the primary prompt injection defence.

chat_answer.yaml is mode-parameterised:
  The YAML contains template variables {mode_system_block}, {context_label},
  {no_context_label}, {suggestions_example} which builder.py fills in based
  on the session's chat_mode before sending to the LLM.

  study mode injects:
    mode_system_block   → educational assistant persona, answer from course content
    context_label       → "COURSE CONTENT CONTEXT"
    no_context_label    → "the course material doesn't cover this topic"
    suggestions_example → examples including quiz_me, visualize, explain_more

  support mode injects:
    mode_system_block   → support assistant persona, KB-strict rules (never invent,
                          always say NO_CONTEXT if not in KB, no quiz/visual suggestions)
    context_label       → "KNOWLEDGE BASE CONTEXT (retrieved from support articles)"
    no_context_label    → "the knowledge base has no information on this topic"
    suggestions_example → follow-up question examples only (no quiz/visual)

  Orchestrator also post-filters: strips any quiz_me or visualize suggestions
  from the LLM response for support mode sessions (two-layer enforcement).

Prompt versioning: get_prompt_version(prompt_name) returns a version hash
embedded in every AIOutput row so quality regressions can be traced.

SECURITY NOTES
---------------
- API keys: SHA-256 hashed at creation, raw key shown once only
- No PII stored in Qdrant payloads (only content text + IDs)
- Prompt injection: 16 weighted pattern scorer (score ≥ 3 = blocked message)
- Unicode: NFKC normalisation prevents homoglyph attacks
- Error responses: never expose stack traces or internal details
- tenant_id on every query: cross-tenant access architecturally impossible
- Redis rate limiter fails open (Redis outage ≠ student lockout)
- MASTER_API_KEY protects admin endpoints (separate from tenant keys)
- Content hash: prevents re-processing unchanged content (cost control)
- Celery tasks: job_id passed explicitly — no ambient state between tasks
